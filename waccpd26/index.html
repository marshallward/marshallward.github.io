Fortran describes independent work

Independent grid points

do concurrent (k=1:nk, j=1:nj, i=1:ni)
  a(i,j,k) = b(i,j,k) + c(i,j,k)
enddo

Every (i,j,k) iteration is independent.

do concurrent does not itself require GPU execution.

[2:30–3:10] The loop is standard Fortran, not a GPU-specific directive. It states that these iterations may execute in any order. The compiler and build configuration decide how to execute them. NVIDIA maps these loops through its OpenACC machinery; other vendors have their own implementations. The source expresses the algorithmic independence while the compiler chooses launch details. But this is not a complete accelerator programming model: Fortran does not prescribe host-device transfers, and procedure calls and temporary storage still affect whether a useful kernel can be generated.

Concurrent slices, ordered integration

Parallel columns within each slice

do concurrent (j=1:nj)
  do k=1,nk
    do concurrent (i=1:ni)
      s(i,j) = s(i,j) + u(i,j,k)
    enddo
  enddo
enddo

Concurrent j slices and i columns; serial accumulation in k.

[3:50–4:30] Flattening this into one concurrent loop would be wrong: each column's accumulation must retain its validated vertical order. Different j slices are independent, and within each slice the i loop updates independent columns side by side. This j-k-i traversal preserves the contiguous i dimension useful to CPU execution. The column and slice versions expose related horizontal independence but organize the ordered vertical work differently. For this pattern NVIDIA can choose 32 by 4 thread blocks; that is a compiler choice, not a Fortran guarantee. The sketch shows computational dependencies, not CUDA launch geometry.

Blocking reconciles CPU and GPU

do concurrent expresses independence; the GPU compiler forms kernels.

Blocking chooses the work region — same solver, different extents.

[4:30–5:30] Distinguish concurrency from a kernel. Fortran do concurrent describes independent iterations, not a GPU launch. In our GPU compilation path these loops also delimit work the compiler turns into kernels; the exact mapping and kernel formation are compiler decisions, not Fortran guarantees. We therefore introduce a computational blocking layer to choose how much work is presented at once. On CPUs we select cache-friendly parts, illustrated by a layer on the left. On GPUs we expose a larger work region, illustrated by the whole local domain on the right, and let the compiler map its independent iterations onto GPU threads and thread blocks. Shading denotes the work region, not concurrency in every dimension: ordered k work can remain serial inside the kernel. The picture is an illustrative contrast, not a requirement to launch the entire domain or a claim that GPU hardware solves algorithmic dependencies. Computational blocks also bound temporary storage and keep control flow outside compact kernels. Runtime extents preserve the same solver and module API; these algorithmic tiles are distinct from CUDA thread blocks.

Traverse blocks, launch local kernels

do jsb=js,je,njj ; do isb=is,ie,nii
  jeb = min(je, jsb+njj-1)
  ieb = min(ie, isb+nii-1)
  iie = ieb - isb + 1
  jje = jeb - jsb + 1

  do concurrent (jj=1:jje, ii=1:iie)
    i = isb + ii - 1
    j = jsb + jj - 1
    ! Work on this block
  enddo
enddo ; enddo

The blue boundary shows each GPU kernel. The CPU steps through each block.

Keep the data on the device

Fortran has no host/device model. OpenMP manages transfers.

We rely on OpenMP–do concurrent interoperability.

[6:45–7:45] So far we have deliberately left out data movement. Exposing independent work and choosing useful blocks is not enough if every kernel copies its fields back and forth. Standard Fortran has no notion of host and device, and thus no means to explicitly control transfers between them. Leaving that distinction outside the language is a reasonable design choice, but we must supply this missing piece. We use OpenMP target enter data and target exit data to manage the lifetime shown here. Inputs use map(to: b, c), output storage uses map(alloc: a), and exit uses map(from: a) and map(delete: b, c). Intermediate host access, when needed, can use target update without ending residency. Solid gold arrows show data transfers; dashed white arrows show successive kernel launches, not copies of resident fields. Real model timesteps contain thousands of kernels, so those transfers would be devastating. Persistent fields are mapped during initialization and retained on the GPU. Modules manage their own temporary storage. The significant design decision is mixing OpenMP data management with do concurrent kernels lowered through OpenACC in this toolchain. Those kernels must resolve OpenMP-managed arrays to the same resident device allocations. This interoperability is an explicit toolchain requirement, not a guarantee of Fortran or a portable assumption about arbitrary OpenMP and OpenACC implementations. The persistent fields remain resident across kernels and timesteps. Derived types require care as well: mapping the object and its array components is one coordinated lifetime problem.

Independence is not enough

Standard Fortran exposes the work; compilers determine the mapping.

[13:15–14:00] One closing example of the gap between independence and an efficient mapping. This is the separate SCA27 continuity-correction study, not the GH200/EPYC benchmark. Layer-wise vertical sums keep i contiguous and k ordered, but require repeated worksharing within a Newton iteration. The column-wise form gives each horizontal face to a thread, which runs its own Newton solve and serial k loops and can stop when that face converges. This is more than a simple loop interchange: convergence control and private iteration state change too. Both forms keep each vertical sum ordered. The colored rows and columns depict solver structure, not a guaranteed team or warp mapping. At 512 by 512 with 100 layers, the rewrite makes this component about 1.6 times slower on the 104-core Intel Xeon node, 1.9 times faster on H200, and 10.2 times faster on one MI250X GCD. AMD benefits especially because amdflang's layer-wise lowering incurs repeated generic-mode worksharing overhead; the column form uses SPMD lowering. The difference reflects source, compiler, runtime, and hardware, not a controlled hardware ranking. The AMD component uses a separate explicit-OpenMP source; it is not a full AMD dynamic-core port or evidence that unchanged do concurrent works equally well everywhere. Standard Fortran takes us far, but expressing independence alone does not guarantee an efficient mapping with today's compilers. The vertical subslide retains the detailed limitations.
